# Build / Merge / Pause decision gates — Dubai 150

**Decision class:** pre-investment portfolio architecture, 2026-10-29. **Not** a statement of organizer judging weights, app readiness or approved expenditure.

## Immediate decision: FREEZE bulk development

No additional generation of 150 separately branded but behaviorally identical UI modules, no deployment or app-store packaging, and no generalized AI access to tools. Preserve all 150 identifiers, research files and both platforms. Spending beyond previously authorized resources, enrollment of private users, contacting partners or activating third-party providers requires explicit permission.

Existing 100 PE/BU "individual modules" are **mission-specific metadata wrappers around one shared `OfflineDraft.preview` formatter**, not specialized autonomous agents. In Stage166, 31/50 Societal pairs used integer-input demos. The architecture must reverse this mistake by demonstrating **one real, well-bounded task** before multiplying runtime code.

## Decision states (each of 150 mission IDs)

- **D0 INVENTORY / HOLD** — name, job hypothesis, scope, documented alternatives. **All 150 currently here.**
- **D1 NEED VERIFIED** — documented, consented users/buyers, observed severity and actual task, task completion with existing alternatives, disconfirming observations recorded.
- **D2 DISTINCT JOB OR EXPLICIT MODULE** — side-by-side A/B/combined/incumbent test clarifies independent outcome and actor/contract boundary. Output is **STANDALONE_CANDIDATE**, **ROLE_CLIENT**, **CAPABILITY_MODULE**, **PIVOT**, or **STOP**; all remain provisional.
- **D3 ARCHITECTURE AND SAFETY APPROVED** — bounded context and data owner, risk classification, least-privilege tool contract, verified source/UNKNOWN policy, threat model, mobile accessibility test design and qualified reviewer.
- **D4 FUNCTIONAL AGENT VERIFIED** — exact goal → independently inspectable plan → scoped tool action in approved sandbox → verifiable receipt → failure/rollback; native Android/iOS compile/device test where relevant. A local preview alone cannot pass.
- **D5 CAUSAL OR CREDIBLE COMPARATIVE BENEFIT** — prospective cohort and outcome measure, true incumbent baseline, independent adjudication, harms/costs, uncertainty. A screen count is not impact.
- **D6 CONTEST / RELEASE REVIEW** — check active rules, original work/license, external terms, security/accessibility, demo reproducibility, team eligibility; explicit user permission before submitting, releasing or spending. No prize result predicted.

No automatic D0→D1 or D1→D3. A rename, a PR, a marketing page, a competitor list or a metric definition is **never** sufficient evidence.

## Decision rules for 45 existing overlap groups

- 13 `HIGH_RESEARCH_MERGE` groups → **PAUSE_DUPLICATE_FRONT_END_ENGINEERING**. Candidate one user journey with configurable modules; evaluate against separate alternatives. This is **not** 13 mandated mergers.
- 18 `SHARED_CORE_DIFFERENT_ROLES` groups → propose **ONE_CAPABILITY_MULTIPLE_AUTHORIZED_CLIENTS**, prove audience, contract and data responsibility differences. User role does **not** automatically justify a separate award entry.
- 14 `ADJACENT_NOT_DUPLICATE` groups → preserve risk-specific behavior, reuse only generic low-risk code. No merging rules for emergency, food safety, clinical support, payments or worker monitoring.

The file `collision_decisions_45.csv` gives decision path for *every* original Stage172 group, shows whether it crosses one or several bounded contexts, and flags the context interface contract. 11 groups cross more than one context and can **never use a shared mutable domain record without authorization**.

### Product shape criterion (per mission)

Choose **STANDALONE_CANDIDATE** only if all are materially distinct and evidenced:
1. Target user/buyer and decision authority
2. Goal and outcome that cannot be reached as an existing app workflow without substantial disadvantage
3. Domain-specific action with an appropriate real tool and explicit review
4. Different permission/data/compliance envelope or value proposition
5. Credible unit economics / deployability / maintainability

If (1)–(5) are not satisfied, prefer a **CAPABILITY_MODULE or ROLE_CLIENT** on the same engine; if evidence refutes need, **STOP**. Don't claim the official competition allows treating an unbundled skill as an independent functional entry without confirming organizer rules.

## Three proposed proof-of-architecture research experiments (NOT authorized live pilots)

### EXP-01 — Accessible venue task: AE-10 JALIS / PE-35 TAHAQQOQ / BU-34 MUYASSAR
**Same fictional task:** user needs exact entrance/route/access condition confirmed on a real permitted venue. **Controls:** direct official venue contact, official accessibility information, and single-app vs separated app prototypes. **Deliverable:** whether a visitor view and venue corrective workflow differ in real-world goals, and authority boundary specification. **Primary outcomes:** critical questions reliably confirmed / total; false VERIFIED count; time. **Stop/pivot:** if current official/mapping options resolve the task, do not release another venue directory. Privacy: user accommodations cannot become publicly searchable.

### EXP-02 — Repair closed loop: AE-21 NADAA / BU-01 IGLAQ / AE-23 NUR / BU-31 TABRID / AE-24 HADAR / BU-32 ISLAH
**Same synthetic incident:** leak or AC malfunction, tenant report, technician inspection, review, disputed closure. **Controls:** incumbent CMMS + DEWA Smart Living and manual tenant exchange. **Deliverable:** one `MaintenanceCase` model with incident subtype and actor-specific state transition. **Primary outcomes:** tenant-confirmed closure, wrongful "resolved" rate, total handling effort. **Stop/pivot:** if resident and facilities functions are already covered, do not replicate incumbent. No fictional sensor anomaly is real diagnostic evidence.

### EXP-03 — AP discrepancies: BU-06 TASWIYA / BU-08 TATABUQ / BU-10 TANBIH
**Same synthetic case:** invoice/PO/receipt discrepancy plus recurring charge review. **Controls:** current Microsoft Dynamics/Oracle feature, manual mail, proposed integrated review. **Deliverable:** one `InvoiceException` subtype protocol, AP-controller sign-off boundary and policy. **Primary outcomes:** independently valid resolution/elapsed time, incorrect payment approvals, repeated contacts. **Stop/pivot:** if ERP native exception handling suffices, don't build a competing thin wrapper. Never send real invoices or alter ERP.

The experiments above are **design proposals only**. No recruitment, user consent, partner access, sample-size power analysis or outcome measurement completed. D0 remains HOLD.

## Architecture-level Definition of Done — before any costly engineering authorization

- [ ] Each proposed product has written source-grounded unmet-need evidence and independently task-tested incumbent workflow
- [ ] 13 merger hypotheses have a documented falsifiable test design; 45 groups have accountable reviewer and case outcome
- [ ] Product-shape decision attached to stable ID; none promoted from mere similarity heuristic
- [ ] Bounded context owns required data; cross-context contract enforces source, role, purpose, consent and retention
- [ ] Domain safety leader and privacy expert review child/health/worker/financial/food/emergency workflows
- [ ] Threat-model tests cover agentic prompt injection, tool misuse and cross-tenant data leakage
- [ ] Real agent behavioral test designed, not just numerical demo or shared local preview
- [ ] 100% of builds claimed as successful have actual CI or device logs; real tool calls not simulated as successes
- [ ] Evidence, adverse events and privacy risks trace to immutable agent IDs even if Latin/Arabic branding changes
- [ ] No contest eligibility, submission, prize or measurable benefit claimed without independent proof

## Resource allocation decision

**Now permitted:** research curation, architecture documentation, synthetic data policies and defensive unit tests, source provenance, competitor comparison protocols. **Not approved:** paid contractors, marketing, 150 individualized apps, app-store release, partner integrations, credential provisioning, account access or public beta. Do not infer allocation of money/headcount/dates from this ADR.

### Review outcome

**APPROVED FOR RESEARCH-ONLY ARCHITECTURE DESIGN** — no authorization to deploy or begin 150 production builds. All 150 `RESEARCH_HOLD`, 450 older delivery gates NO-GO, no automatic merge or rename.
